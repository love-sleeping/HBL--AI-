# HBL --- Hierarchical Block Lifecycle Architecture

### 一种模块化 AI 代码生成架构构想

> 让 AI 像搭积木一样编写程序，让程序像一棵树一样生长。

**TREE · FRAME · BANANA · LEGO · SLEEP**

**CHECK · GROW · LAB · SAVE**

------------------------------------------------------------------------

## 项目简介

HBL 是一种面向大型软件项目的模块化 AI 代码生成架构构想。

它希望改变 AI
编写复杂程序的方式：不再仅仅依赖一次次生成代码、修改代码，而是先建立完整的项目结构，再逐步搭建主干、寻找需要开发的分支，并通过独立模块完成整个项目。

HBL 的核心思想可以概括为：

-   用 TREE 规划整个项目。
-   用 FRAME 搭建程序主干。
-   用 BANANA 寻找值得开发的分支。
-   用 LEGO 组合、拆卸和替换模块。
-   用 SLEEP 管理模块的休眠与唤醒。
-   用 CHECK 检查代码质量。
-   用 GROW 让项目根据需求持续生长。
-   用 LAB 测试新模块。
-   用 SAVE 保存项目状态并支持恢复。

**HBL 希望让 AI
不仅能够编写代码，还能够持续管理和发展一个完整的软件项目。**

> 项目状态：概念设计与研究阶段。本文描述的是设计目标，不代表所有功能已经实现。

------------------------------------------------------------------------

# 01. 为什么提出 HBL？

随着 AI 编程能力的发展，AI
已经可以帮助开发者编写函数、搭建网站，甚至开发较为复杂的软件。

但在大型项目中，仍然存在一些值得解决的问题：

1.  项目规模越来越大，AI 难以始终掌握全部代码和结构。
2.  修改一个功能，可能意外影响其他功能。
3.  某个模块出现问题时，可能需要重新修改大量代码。
4.  项目需求发生变化后，原有结构可能难以调整。
5.  AI 可能把大量时间花在次要功能上，而忽略真正重要的部分。
6.  项目开发过程中，历史状态、模块版本和依赖关系难以统一管理。

HBL 希望通过结构化规划、模块化开发和动态管理解决这些问题。

它的目标不是让 AI 一次性生成整个项目，而是让 AI 能够：

**规划 → 搭建 → 探索 → 组合 → 检查 → 调整 → 保存 → 再次开发。**

------------------------------------------------------------------------

# 02. HBL 总体架构

HBL 目前由九个核心系统组成。

  系统     中文名称   核心职责
  -------- ---------- ----------------------
  TREE     树         规划程序结构
  FRAME    框架       建立程序主干
  BANANA   香蕉       主动寻找开发目标
  LEGO     积木       组合、替换和复用模块
  SLEEP    睡眠       管理模块休眠与唤醒
  CHECK    检查       检查代码质量
  GROW     生长       根据需求调整程序
  LAB      实验室     隔离测试新模块
  SAVE     保存       保存项目状态和恢复点

# 03. 九个核心系统

## 3.1 TREE ------ 树形结构系统

**让 AI 知道整个项目应该由什么组成。**

在正式编写代码之前，TREE 首先分析用户需求，并把项目拆分成一棵程序树。

例如，我们希望 AI 制作一款无人机飞行游戏：

``` mermaid
flowchart TB
    A["无人机飞行游戏"]

    A --> B["游戏基础"]
    A --> C["飞行系统"]
    A --> D["视觉系统"]
    A --> E["地图系统"]
    A --> F["操作系统"]

    B --> B1["游戏入口"]
    B --> B2["主循环"]

    C --> C1["飞行控制"]
    C --> C2["物理计算"]
    C --> C3["碰撞检测"]

    D --> D1["光照"]
    D --> D2["材质"]
    D --> D3["天气"]

    E --> E1["建筑"]
    E --> E2["道路"]

    F --> F1["键盘输入"]
    F --> F2["鼠标控制"]
```

这棵树代表项目的整体规划。

随着项目发展，TREE
可以继续增加新的分支，也可以根据需求变化调整原有结构。

需要注意，真实的软件模块可能同时被多个功能使用，因此 TREE
还需要配合依赖关系图，不能只依赖简单的树形结构。

**设计目标：让 AI 在写代码之前，先理解项目整体。**

## 3.2 FRAME ------ 主干搭建系统

**先搭建一个可以继续建设的程序框架。**

建造房屋时，我们通常不会先装修每个房间，而是先建立基础结构。

FRAME 采用类似的思路。

它首先生成：

-   程序入口。
-   核心运行逻辑。
-   基础模块接口。
-   模块之间的连接关系。
-   最基本的运行环境。

例如：

``` python
class Game:
    def initialize(self):
        pass

    def update(self, delta_time):
        pass

    def render(self):
        pass
```

这只是一个简单的程序骨架，并不是完整的游戏。

FRAME 真正追求的是建立一个最小可运行、能够继续扩展的主干。

**设计目标：先让项目拥有一个稳定的基础，再逐步增加功能。**

## 3.3 BANANA ------ 分支探索系统

**主动寻找下一步最值得开发的功能。**

为什么叫 BANANA？

可以想象一只猴子在树林里寻找香蕉。

它不会机械地检查每一棵树，而是主动寻找值得前往的方向。

BANANA 也是如此。

当程序树中存在许多尚未完成的分支时，AI
不必严格按照从上到下的顺序开发，而是根据项目情况主动寻找最值得展开的分支。

例如：

  分支       重要程度   当前状态
  ---------- ---------- ----------
  飞行系统   高         未完成
  视觉系统   中         开发中
  音效系统   低         未开始
  地图系统   高         未完成

BANANA 需要综合考虑：

1.  这个功能对最终项目有多重要？
2.  它是否是其他功能的前置条件？
3.  它目前完成了多少？
4.  完成它能带来多大的实际价值？
5.  实现它需要多少时间和资源？

一个初步的分支评分模型可以是：

\[ S_i=w_1R_i+w_2D_i+w_3U_i+w_4I_i-w_5C_i \]

其中：

-   (R_i)：需求相关性。
-   (D_i)：依赖重要性。
-   (U_i)：未完成程度。
-   (I_i)：对项目最终效果的影响。
-   (C_i)：开发成本与风险。
-   (w_1 `\sim `{=tex}w_5)：可调整的权重。

BANANA
不能永远只选择评分最高的分支，否则某些暂时不显眼但实际重要的功能可能一直得不到开发。

因此，它还需要探索机制，定期检查其他分支。

**设计目标：让 AI
根据项目实际情况决定下一步做什么，而不是机械地执行固定顺序。**

## 3.4 LEGO ------ 积木模块系统

**让程序像积木一样自由组合。**

这是 HBL 的核心设计之一。

LEGO 希望将程序拆分成相对独立的模块。

每个模块都可以被单独开发、测试、保存和替换。

例如：

``` mermaid
flowchart TB
    ROOT["飞行系统"]

    ROOT --> A["物理模块 A"]
    ROOT --> B["控制模块"]
    ROOT --> C["碰撞模块"]

    D["物理模块 B"] -. "替换 A" .-> A
```

假设物理模块 A 的性能不够理想。

我们可以开发物理模块 B，在接口兼容的前提下，用 B 替换 A。

理想情况下，其他模块不需要重新编写。

LEGO 希望实现：

-   **组合：** 将多个模块连接起来。
-   **拆卸：** 将不再需要的模块移除。
-   **替换：** 用新模块替换旧模块。
-   **复用：** 在不同项目中使用已有模块。
-   **升级：** 保留旧版本，同时开发新版本。

为了避免替换模块时破坏其他功能，每个模块都需要明确自己的输入、输出、依赖关系和接口规范。

模块信息可以采用类似这样的结构：

``` json
{
  "module_id": "physics_engine",
  "version": "1.0.0",
  "interface": "PhysicsInterface",
  "dependencies": ["input_system"],
  "state": "ACTIVE",
  "replaceable": true
}
```

模块替换不能只依靠名称相同，还需要接口检查和兼容性测试。

**设计目标：让修改尽可能局限在对应模块内部。**

## 3.5 SLEEP ------ 模块休眠系统

**让暂时不需要的模块进入休眠状态。**

大型项目可能包含大量模块，但 AI 不需要在每一个时刻都处理所有模块。

例如，一个游戏的天气系统已经完成，但当前正在开发飞行控制。

此时，AI 可以让天气系统进入休眠状态。

休眠后：

-   暂时不主动读取它的完整代码。
-   保留模块的基本信息。
-   保留模块接口和依赖关系。
-   保留开发进度。
-   需要时可以重新唤醒。

模块状态可以设计为：

``` mermaid
stateDiagram-v2
    [*] --> ACTIVE

    ACTIVE --> IDLE: 暂时不使用
    IDLE --> SLEEP: 进入休眠
    SLEEP --> ACTIVE: 需要使用

    IDLE --> ACTIVE: 重新调用

    ACTIVE --> ERROR: 发生错误
    ERROR --> ACTIVE: 修复成功

    SLEEP --> ARCHIVED: 长期归档
```

需要区分两种休眠：

**AI 上下文休眠：** 减少当前需要处理的信息，但模块仍然保存在项目中。

**程序运行休眠：** 暂停模块实际执行，必要时释放运行资源。

这两种能力需要不同的技术实现。

**设计目标：减少不必要的信息处理和资源占用，而不是删除模块或遗忘模块。**

## 3.6 CHECK ------ 质量检查系统

**判断生成的模块是否真的可以使用。**

AI 写出的代码不一定正确。

即使代码没有语法错误，也可能存在逻辑问题。

CHECK 负责检查：

-   代码是否符合语法要求。
-   模块接口是否正确。
-   输入和输出是否符合约定。
-   单元测试是否通过。
-   模块与其他模块能否正常配合。
-   是否存在明显的安全和性能问题。

如果一个模块没有通过必要检查，就不能直接进入正式项目。

CHECK 需要将错误信息反馈给对应模块，让 AI 尝试修复。

**设计目标：让模块经过验证后再正式使用。**

## 3.7 GROW ------ 动态生长系统

**让程序能够根据新的需求改变结构。**

一个项目的需求并不是永远固定的。

例如，最初我们只想制作一个单人无人机游戏，后来决定增加多人联机功能。

GROW 需要：

1.  理解新增需求。
2.  判断需要增加哪些分支。
3.  分析哪些现有模块受到影响。
4.  尽可能保留可以复用的模块。
5.  修改程序树和依赖关系。
6.  生成或调整必要的模块。

**设计目标：让程序成为一个可以持续变化和扩展的结构。**

## 3.8 LAB ------ 沙盒实验室系统

**在新模块正式加入项目之前，先进行独立测试。**

假设 AI 新生成了一个物理引擎。

我们不能直接把它替换进正在运行的游戏中，因为它可能存在错误，也可能影响其他模块。

LAB 就像一个独立实验室。

新模块首先进入隔离环境，在不影响正式项目的情况下进行测试。

测试内容包括：

-   是否能够正常运行。
-   输入输出是否符合接口要求。
-   是否能够处理异常情况。
-   是否会破坏其他模块的数据。
-   是否满足性能要求。

测试通过后，模块才能进入正式项目。

如果测试失败，就退回修改。

**设计目标：避免未经验证的代码直接影响整个项目。**

## 3.9 SAVE ------ 项目保存与恢复系统

**保存项目状态，让 AI 可以在需要时恢复。**

开发大型项目时，保存的不应该只有源代码。

还应该保存：

-   当前程序树。
-   各模块的版本。
-   模块之间的依赖关系。
-   当前开发进度。
-   测试结果。
-   错误记录。
-   最近一次稳定版本。

例如：

``` text
项目状态
│
├── 版本：0.1
├── 主干：已完成
├── 飞行系统：开发中
├── 视觉系统：已完成
├── 音效系统：未开始
└── 最近检查：通过
```

如果某次修改导致项目出现严重问题，SAVE 可以帮助恢复到之前的检查点。

**设计目标：让项目能够安全地持续修改，而不必因为一次错误重新生成整个项目。**

# 04. HBL 的完整工作流程

九个系统并不是各自独立工作，而是需要形成一个持续循环。

``` mermaid
flowchart TD
    A["用户提出需求"] --> B["TREE 建立程序树"]
    B --> C["FRAME 搭建主干"]
    C --> D["BANANA 寻找开发目标"]
    D --> E["LEGO 生成或组合模块"]
    E --> F["LAB 隔离测试"]
    F --> G["CHECK 质量检查"]

    G --> H{"是否通过？"}

    H -->|否| I["修复或替换模块"]
    I --> E

    H -->|是| J["正式接入项目"]
    J --> K["SAVE 保存状态"]
    K --> L["SLEEP 管理模块状态"]
    L --> M["GROW 调整项目结构"]
    M --> D
```

这意味着 HBL 不只是一次性代码生成工具。

它更接近一个能够持续管理项目结构、模块和开发进度的 AI 编程系统。

# 05. HBL 的 Token 设计

除了程序结构，HBL 还提出了一个关于 AI 内部代码表达方式的想法。

AI 通常通过 Token 来处理文本和代码。

HBL 希望进一步探索：能否让不同类型的 Token 承担更加明确的编程职责？

目前设想分为四类。

### 5.1 结构 Token

负责描述程序的组织结构。

例如：

``` text
ROOT
MODULE
FUNCTION
CLASS
BRANCH
EXPAND
END
```

### 5.2 编程 Token

负责描述编程语言中的语法和操作。

例如：

``` text
if
else
for
while
return
class
import
print
```

### 5.3 数据 Token

负责表示变量、数字、字符串和其他具体数据。

例如：

``` text
player_speed
100
"Hello World"
```

### 5.4 控制 Token

负责控制 HBL 自身的工作过程。

例如：

``` text
WAKE
SLEEP
SEARCH
EXPAND
REPLACE
ROLLBACK
COMMIT
```

这些指令不是最终生成的 Python 或 C++ 代码，而是供 HBL 管理系统使用。

### Token 工作流程

``` mermaid
flowchart TD
    A["HBL Token"]

    A --> B["结构 Token"]
    A --> C["编程 Token"]
    A --> D["数据 Token"]
    A --> E["控制 Token"]

    B --> F["结构解析"]
    C --> F
    D --> G["代码构建"]
    E --> H["系统调度"]

    F --> G
    G --> I["AST 抽象语法树"]
    I --> J["代码生成器"]
    J --> K["实际源代码"]
    K --> L["编译与测试"]
```

这里需要注意：专用 Token 并不意味着一定比普通 Token 更高效。

它是否能够降低计算成本、提高代码正确率，还需要通过实验验证。

# 06. HBL 与常见 AI 代码生成方式的区别

这里的对比描述的是设计目标，并不代表 HBL 已经通过实验取得优势。

  比较项目   常见代码生成方式           HBL 的设计目标
  ---------- -------------------------- ---------------------
  项目规划   根据任务和上下文逐步规划   先建立程序树
  代码组织   文件和代码片段             可管理的功能模块
  开发顺序   根据任务或上下文推进       BANANA 动态选择分支
  模块替换   需要处理相关代码           LEGO 按接口替换
  信息管理   依赖上下文和外部工具       SLEEP 分层管理
  错误恢复   根据情况重新修改           SAVE 检查点与回滚
  需求变化   修改现有代码               GROW 调整程序结构

现有 AI 编程工具也已经具备规划、模块化、测试和项目索引等能力。

HBL
并不是认为这些技术从未出现过，而是希望探索一种更加统一、结构化的组合方式。

# 07. 目前存在的问题

HBL 目前仍然是一个架构构想，距离真正实现还有不少工作。

主要问题包括：

1.  **程序树如何设计？** 需要明确节点、分支、依赖和拆分规则。
2.  **模块如何互换？** 需要统一接口规范，保证替换不会破坏其他模块。
3.  **BANANA 如何选择目标？** 需要设计优先级、依赖判断和探索算法。
4.  **SLEEP 如何管理依赖？** 需要防止休眠模块影响仍在运行的模块。
5.  **如何验证代码质量？** 需要建立自动化测试和质量检查机制。
6.  **Token 是否真的有优势？** 需要与现有 Token 表达方式进行对照实验。
7.  **如何控制系统成本？** 复杂的管理机制本身也会消耗时间和计算资源。

这些问题都需要通过设计、开发和实验逐步解决。

# 08. 未来开发计划

HBL 不应该一开始就实现所有功能。

更合理的方式是先建立一个小型原型，再逐步增加能力。

  阶段       主要任务           目标
  ---------- ------------------ ------------------------------
  第一阶段   TREE、FRAME        实现程序树和主干生成
  第二阶段   LEGO               实现模块独立生成和替换
  第三阶段   BANANA、SLEEP      实现智能调度与模块休眠
  第四阶段   CHECK、LAB、SAVE   实现质量检查、沙盒测试和恢复
  第五阶段   GROW               实现动态调整与项目进化
  第六阶段   Token 系统         探索更结构化的代码表达方式

# 09. 如何判断 HBL 是否成功？

一个架构不能只靠概念和想法来证明自己。

HBL 最终需要通过实验验证。

建议重点比较以下指标：

  指标             研究目的
  ---------------- --------------------------------
  代码正确率       生成的程序是否正确
  测试通过率       项目能否正常运行
  Token 消耗       是否减少计算和上下文成本
  修改范围         修改一个模块会影响多少其他模块
  模块替换成功率   是否能够可靠替换模块
  回滚成功率       出错后能否恢复
  开发时间         是否提高开发效率
  分支探索覆盖率   是否遗漏重要功能

实验时，应当尽可能使用相同的模型、任务和测试条件，对比 HBL 与常见 AI
编程流程。

只有取得可重复的实验结果，才能判断 HBL 是否真正带来改善。

# 10. 项目愿景

我们希望未来的 AI 不只是一个能够生成代码的工具。

它还应该能够理解一个项目的整体结构，知道每个模块的职责，判断下一步应该做什么，并在发生错误时尽可能只修复有问题的部分。

我们希望程序不再只是一次性生成的代码集合，而是一套能够持续生长、组合、替换和恢复的系统。

**先搭建框架，再寻找方向；先完成模块，再组合成整体。**

这就是 HBL 想要探索的方向。

# 11. 项目声明

HBL 目前处于概念设计和研究阶段。

本文介绍的是架构设想，不代表所有系统已经实现，也不代表其性能已经得到验证。

其中涉及的树形规划、模块化设计、任务调度、懒加载、自动测试和版本恢复等思想，在已有的软件工程和
AI 系统中均能找到相关技术基础。

HBL 的研究重点是探索这些机制能否形成一个统一、动态、可扩展的 AI
代码生成与项目管理架构。
